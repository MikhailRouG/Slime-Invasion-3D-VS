# Code Review — Slime Invasion (DirectX 11)

Аудит кодовой базы с точки зрения найма: слабые места, приоритеты и дорожная
карта приведения проекта к принципам OOP и SOLID. Документ можно показывать
на собеседовании — он демонстрирует, что вы понимаете сильные и слабые стороны
собственного кода.

---

## 1. Краткая оценка

**Что уже хорошо:**
- Работающая 3D-игра на «голом» DirectX 11: свой рендер, шейдеры (Phong-освещение,
  shadow map, billboard, particles), загрузка моделей через Assimp, скелетная
  анимация, звук, сцены, UI.
- Иерархия врагов (`Enemy` → `EnemyNormal`) уже сделана через **паттерн State**
  с полиморфизмом — это правильный ООП-подход, его стоит распространить на остальной код.

**Главная слабость:** архитектура в целом **процедурная (C-style)**. Каждый модуль —
это набор свободных функций с префиксом (`Light_`, `Player_`, `Camera_`, `Scene_`)
поверх глобальных `static`-переменных. Это работает, но нарушает инкапсуляцию,
мешает тестированию и переиспользованию, и на собеседовании по C++/геймдеву
сразу считывается как «учебный» стиль.

## 2. Найденные дефекты (по убыванию критичности)

| # | Файл | Проблема | Статус |
|---|------|----------|--------|
| 1 | `enemy.h` | `GetPosition()` возвращал `return {0,0,0};` — **ссылку на временный объект (UB)**. Крах/мусор при вызове базовой версии. | ✅ Исправлено |
| 2 | `enemy_normal.h` | `GetScaleByLvl()` объявлен `int`, а поле `m_ScalebyLvl` — `float` (1.0, 1.1, 1.2…). Дробная часть **отбрасывалась**, масштабирование по уровню молча не работало. | ✅ Исправлено |

### 🟠 Важные (архитектура и надёжность)

- **Глобальное изменяемое состояние повсюду.** Почти каждый `.cpp` держит данные в
  `static`-переменных файла. Следствия: невозможен второй экземпляр (сплит-скрин,
  юнит-тест), скрытые зависимости через порядок инициализации, гонки при многопоточности.
- **Нет RAII, ручное управление ресурсами.** Макрос `SAFE_RELEASE` и парные
  `*_Initialize/*_Finalize` вызываются вручную. Любой ранний `return`/исключение →
  утечка COM-объекта. `new EnemyNormalStatePatrol(...)` в конструкторе (`enemy_normal.h`)
  без `delete`/умного указателя — неясное владение и утечки состояний.
- **HRESULT игнорируется.** `CreateBuffer`, `CreateTexture`, `Map` и т.п. вызываются
  без проверки кода возврата. При сбое драйвера — тихий `nullptr` и падение позже.
- **`Scene_*` — гигантский `switch` (нарушение Open/Closed).** В `scene.cpp` шесть
  функций (`Update/Draw/Finalize/Push/…`) дублируют один и тот же `switch` по типу
  сцены. Добавление новой сцены = правка 6 мест. Просится полиморфная база `IScene`.

### 🟡 Средние (читаемость / профессионализм)

- **Mojibake в комментариях.** Множество файлов содержит комментарии в Shift-JIS,
  которые в UTF-8 выглядят как «крякозябры» (`light.cpp`, `direct3d.h`, `main.cpp`,
  `title.cpp`…). Для ревьюера это выглядит неаккуратно. → Перекодировать в UTF-8 или
  перевести на английский (как сделано в `light.*`).
- **Мёртвый код.** Пустое тело `Map_Rendering()`, закомментированные блоки в
  `main.cpp`, `player_camera.cpp` (убрано), `game.cpp`.
- **Магические числа.** `256, 256`, `0.8f`, `0.04f`, `12.0f`, `{0.45f,…}` в `game.cpp`
  без именованных констант.
- **Опечатки в идентификаторах.** `m_PoimtX` (→ `m_PointX`), `Projction`
  (`Direct3D_SetLightViewProjctionMatrix`), смешение стилей именования
  (`g_`, `m_`, `camelCase`, `PascalCase`).
- **«God includes».** `game.cpp` подключает ~30 заголовков — признак того, что модуль
  делает слишком много (инициализация, апдейт, отрисовка, освещение, UI…).

## 3. Что уже сделано в этом проходе

1. **Исправлены баги** #1 и #2 (UB и усечение `float`→`int`).
2. **Модуль освещения переписан в ООП/SOLID** как эталон (`light.h`/`light.cpp`):
   - класс `LightRenderer` — **Single Responsibility** (только управление
     constant-буферами света);
   - **Dependency Inversion** — `ID3D11Device*`/`Context*` передаются в конструктор,
     а не берутся из глобала;
   - **RAII** через `Microsoft::WRL::ComPtr` — буферы освобождаются автоматически,
     ручной `Finalize` не нужен, утечки невозможны;
   - класс некопируемый (запрет копирования владеющего ресурсами объекта);
   - добавлена защита от выхода за границы в `SetPointLight`;
   - **обратная совместимость**: старые `Light_*`-функции сохранены как тонкий
     фасад над одним экземпляром класса — **ни один вызывающий код не сломан**,
     раскладка constant-буферов (b1–b4) осталась байт-в-байт прежней.
3. **Улучшено изображение меню** (`resource/texture/MainMenu.png`): убран водяной
   знак AI-генератора, добавлены аккуратная резкость, контраст, насыщенность и
   лёгкая виньетка для акцента на заголовке.
4. **Убран мёртвый код** в `player_camera.cpp`.

5. **Проект разложен по папкам** (116 исходников + 13 шейдеров перенесены через
   `git mv`, история файлов сохранена):

```

  render/    shader*, sprite, texture, model, light, billboard, particle, ...  (50)
```

   В корне остались только файлы решения, `CODE_REVIEW.md` и `assimp-vc143-mt.dll/.lib`
   (их трогать нельзя — см. §2). Неиспользуемый `ball.fbx` убран в `resource/model/`,
   дубликат `MainMenu2.png` удалён (был байт-в-байт равен `MainMenu.png`).

   - `.vcxproj` и `.vcxproj.filters` перегенерированы (129 записей), дерево в
     Solution Explorer совпадает со структурой на диске;
   - все папки добавлены в `AdditionalIncludeDirectories`, поэтому **все
     существующие `#include "foo.h"` работают без правок** — не пришлось трогать
     116 файлов;
   - проверено скриптом: **0 несуществующих путей в проекте, 0 неразрешённых
     инклюдов**.

6. **Починен конвейер шейдеров** (это была скрытая проблема): раньше `FxCompile`
   складывал `.cso` в `$(OutDir)`, а игра грузила **закоммиченные** `.cso` из
   `resource/shader/` — то есть *правки `.hlsl` не влияли на игру* до ручного
   копирования. Теперь задан
   `ObjectFileOutput = $(ProjectDir)resource\shader\%(Filename).cso`, и шейдеры
   компилируются прямо туда, откуда читает рантайм. Заодно устранена
   несогласованность: billboard-шейдеры грузились из корня, а не из
   `resource/shader/` — теперь все 12 грузятся единообразно.

`LightRenderer` — это шаблон, по которому имеет смысл переписать остальные модули.

## 4. Дорожная карта до полного OOP/SOLID

Порядок — от быстрых побед к крупному рефакторингу. Делать **инкрементально**,
компилируя после каждого шага (одномоментный переписыватель всего проекта
гарантированно сломает сборку).

**Этап 1 — гигиена (1 день):**
- перекодировать комментарии в UTF-8 / английский;
- удалить мусорные файлы и вынести бинарники из git;
- завести `.editorconfig` и единый стиль именования.

**Этап 2 — RAII и инкапсуляция (по модулю за раз):**
- по образцу `LightRenderer` завернуть `Camera`, `Player`, `Bullet`, `Sky`,
  `Direct3D`, шейдеры в классы; глобальный `static` → приватное поле;
- заменить `SAFE_RELEASE` + сырые указатели на `ComPtr`;
- сделать `*_Initialize/*_Finalize` конструктором/деструктором.

**Этап 3 — полиморфизм сцен (Open/Closed):**
```cpp
class IScene {
public:
    virtual ~IScene() = default;
    virtual void Update(double dt) = 0;
    virtual void Draw() = 0;
    virtual void OnClick(int x, int y, bool pressed) {}
};
// TitleScene / GameScene / EndScene : public IScene
// SceneManager хранит стек std::unique_ptr<IScene>;
// шесть switch в scene.cpp схлопываются в вызовы виртуальных методов.
```
Это убирает дублирование `switch` и делает добавление сцены = одному новому классу.

**Этап 4 — развязка зависимостей (Dependency Inversion):**
- ввести интерфейс рендерера/устройства и передавать его в подсистемы, а не
  тянуть `Direct3D_GetDevice()` из глобала;
- это же откроет дорогу к юнит-тестам (мок-устройство).

**Этап 5 — восстановить и инкапсулировать столкновения:**
- вернуть отключённую логику из `game.cpp` в отдельный `CollisionSystem`
  (Single Responsibility), а не в тело `Game_Update`.
